> 在积分过期之前，把每一分都花在单位价值最高的去路上。

基于**麦当劳中国官方 MCP** 的 AI Skill：把「麦麦商城兑换」和「积分抽奖」两条去向折算到同一个尺子上比较，用背包 DP 在清算预算内求出最优组合，并对到期日发出预警。

---

## 它解决什么问题

积分是有**时效**的资产，但大多数人面对它时只有三个动作：攒着、到期前随手换一个、忘了它。真正的问题是：

- 不知道自己有多少积分**即将过期**
- 不知道换哪个商品的**单位价值最高**
- 不清楚**抽奖**是否真的比**直接兑换**划算
- 手里有一笔预算，却凑不出总价值最大的组合——贪心地按单价从高到低买，最后总会剩下一堆无处安放的零碎积分，照样过期

本项目把这四件事变成可计算的步骤，最后产出一份**带数字、可直接执行**的兑换清单。

---

## 两个容易踩的坑

这两条都是在真实接上 MCP 之后才发现的，也是本项目与「看起来很聪明」的实现之间真正的差别。

### 坑一：券面价不是你赚到的钱

麦麦商城里大量商品是「凭券享 X 元购买」券。比如一张 **100 积分**兑换的「3.9 元圆筒冰淇淋券」，直觉算法会得到 `3.9 ÷ 100 = 39 元/千积分`——**这个数是错的**。官方商品详情里写得很清楚：

> 凭本券可享受 **3.9 元购买**圆筒冰淇淋

兑换之后你**还要再付 3.9 元**。同一份文档还给出了官方自己认可的比价基准：

> …是与不参加优惠活动情况下单独购买该产品的**常规价格（或者其中所含单品的常规单买价总和）**相比较

所以正确的算法是：

```text
一张券的价值 = Σ(券内单品 × 各自常规菜单价) − 凭券应付的现金
VPP        = 该净价值 ÷ 积分价
```

常规菜单价不是拍脑袋估的，而是 `query-meals` 拉到的**真实门店报价**：

| 券 | 常规价 | 应付 | 净价值 | 积分价 | VPP |
|---|---|---|---|---|---|
| 16.9元2份麦辣鸡翅 | ¥30.0（15×2） | ¥16.9 | ¥13.1 | 200 | 65.5 |
| 22.9元2份板烧鸡腿堡 | ¥47.0（23.5×2） | ¥22.9 | ¥24.1 | 500 | 48.2 |
| 21.9元巨无霸可乐组合 | ¥35.0（25.5+9.5） | ¥21.9 | ¥13.1 | 800 | 16.4 |

按错误的券面价口径，第一行会被算成 `16.9 ÷ 200 = 84.5 元/千积分`，虚高约 **29%**。

### 坑二：抽奖的期望值算不准，因为官方不公布概率

真实调用 `query-lottery-info` 会拿到完整奖品池（本次 27 项，含「下单立减 3 元券」「麦辣鸡腿汉堡 5 折优惠券」「28 会员积分」等），但每一项**只有 `name` / `imageUrl` / `typeText`，没有任何中签概率**。

没有概率就没有真正的期望值。本项目的做法是：按奖品名称里的规则逐项折价（立减券按面额、折扣券按 `(1−折扣)×常规价`、积分奖按本单位积分价值），然后在**等概率**假设下算出参考期望值，并把假设明确写进结论。

关键在最后的取舍：真实奖池通常把低价券放在高概率档，等概率假设几乎必然**高估**。所以概率未知时，本项目不拿这个数替用户拍板，而是退回收益确定的兑换——这也是它的默认行为。缺少可靠依据时不给建议，本身就是一种建议。

## 三步核心机制

### 1. 估值：把不同去向折算到同一把尺子

```text
VPP = 兑换到手的净价值 ÷ 商品积分价   （单位：元 / 积分，展示用「元 / 千积分」）

对「凭券享 X 元购买」类券，净价值 = 券内单品的常规菜单价合计 − 凭券应付现金。
直接用券面价当价值会把结论抬高约三成，详见上文「坑一」。
```

能精确算的精确算；不能精确算的**明确标注，不假装算得准**：

| 情况 | 处理 | 标注 |
|---|---|---|
| 能核到单品的真实菜单价 | `Σ(单品×常规价) − 应付` ÷ 积分价 | 【准】 |
| 只有积分价，同类目有样本 | 同类目 VPP 中位数 | 【估】 |
| 只有积分价且同类目无样本 | 全站 VPP 中位数 | 【估】置信度低 |
| 无任何可比价格 | 排除出推荐 | — |

### 2. 决策：抽奖 vs 兑换，按风险定价

```text
调整后抽奖价值 = 单位期望价值 × (1 − 不确定度 × 惩罚系数)
抽奖门槛      = 最佳商品 VPP × (1 + 溢价要求)
```

抽奖的不确定性体现在两个系数里：**不确定度**（概率已披露取 0.25，未披露取 0.60）与**风险偏好**。

> 真实的 `query-lottery-info` **不返回任何概率**，因此不确定度一律取 0.60；
> 且当概率未知时，本项目会直接回到确定收益的兑换，不再拿假设出来的期望值给用户做决策。

| 风档 | 惩罚系数 | 溢价要求 | 适用 |
|---|---|---|---|
| 保守 | 0.90 | 20% | 稳一点，不冒险 |
| 均衡 | 0.50 | 8% | 默认 |
| 激进 | 0.15 | 0% | 就想抽一把 |

### 3. 择优：背包 DP，而不是贪心

「怎么在预算内凑出总价值最大」是背包问题。**按单价贪心会留下大量无处安放的零碎积分**，因此用 0/1 背包 DP 求解，并输出预算利用率。

> 默认**只让有官方现金价的商品**参与择优。估算商品虽然 VPP 可能好看，但那个数字本身是推算出来的——让推算值主导最优化，等于用假数字替你做决定。它们会被单独列进「待定清单」，交给你自己判断。需要纳入时加 `--include-estimated`。

## 安装方法

**前置条件**：在 <https://open.mcd.cn/mcp> 用手机号登录后申请 MCP Token（约 1 分钟）。

```bash
# 1. 获取代码
git clone https://github.com/sunqichao/mcd-points-sunset.git
cd mcd-points-sunset

# 2. 配置 Token（.env 已被 gitignore，不会误提交）
cp .env.example .env
#   编辑 .env，把 MCD_MCP_TOKEN 换成你的真实 Token

# 3. 运行清算（只读，不会消耗任何积分）
python3 src/pipeline.py
```

Python 3.9+，**无需 pip install**——全部依赖标准库。

未申请 Token 也能立刻看到完整效果：

```bash
python3 src/pipeline.py --mock      # 用内置样例数据跑通全链路
python3 tests/test_core.py          # 28 项算法断言
python3 src/build_demo.py           # 生成可视化看板 demo/index.html
```

### 在 WorkBuddy / Claude / Cursor 中作为 Skill 使用

将 [`mcp-config.example.json`](./mcp-config.example.json) 的内容粘贴到 MCP 配置中并替换 Token，然后启用 `SKILL.md`。之后直接对话即可：

> 「我的麦麦积分怎么花最值」
> 「积分还有多久过期」
> 「用积分抽奖划算吗」

## 安全设计

这是本项目最在意的部分——它能触达的是**用户真实的积分资产**：

- **默认只读**。常规运行只调用 7 个查询类工具（`query-my-account`、`mall-points-products`、`mall-product-detail`、`query-lottery-info`、`now-time-info`、`query-nearby-stores`、`query-meals`），**绝不**调用 `draw-lottery` / `mall-create-order`
- **双开关写保护**。即便显式要求执行，也需同时通过 `--execute` 与 `--i-know-this-costs-points`
- **凭证隔离**。Token 只从环境变量读取；仓库内只有 `${MCD_MCP_TOKEN}` 占位符，`.gitignore` 已排除 `.env` 与真实响应产物
- **知情而非代劳**。估算商品不参与自动择优；抽奖「谢谢参与」类奖品按 0 值参与期望计算，避免系统性高估抽奖收益
